# 业务自测共享契约 v2

A 设计并确认业务，B 自动映射技术并执行。这里只约定必要的 Markdown 内容，不要求用户填写技术配置，也不引入发布级就绪门禁。

## 范围、快照与产物

- 默认使用 `.self-test/<scope>/` 作为产物根。测试点保存到 `runs/<confirmation-run-id>/test-points.md`，执行报告保存到 `runs/<confirmation-run-id>/executions/<run-id>/test-report.md`，所有文件不可变且不覆盖。A 第一次展示候选载荷就分配 `confirmation-run-id` 并写入一次；用户要求修改时创建新的 id 和文件，旧候选保留为未确认历史。用户确认后另写不可变的 `runs/<confirmation-run-id>/confirmation.md`，不得回写 `test-points.md`。阶段报告写入对应执行目录的 `reports/<sequence>-stage.md`，`sequence` 从 `001` 递增且每个文件只写一次；最终 `test-report.md` 只在收口时写一次。证据和最小复现脚本放在对应执行目录的 `evidence/`、`scripts/`。`confirmation-run-id` 与执行 `run-id` 均用时间戳，冲突时加序号；旧的根级 `test-points.md` 只可读取为草稿基线，新一轮必须写入新的确认目录。技能绝不执行 `git add`、`git commit` 或 `git push`。
- Git 项目默认由 A 在 `.git/info/exclude` 维护 managed block；若现有忽略规则已精确覆盖产物目录，则直接复用且不修改任何忽略文件。只有用户明确选择团队共享忽略规则时，A 才可修改项目 `.gitignore`；该选择不得从已有规则、历史操作或普通自测请求推定。无论写入哪一个忽略文件，都保留原有规则和 managed block 外内容。备用产物目录必须是专用于本轮自测产物的、精确的仓库相对子目录，例如 `qa-output/order/`；只向 managed block 追加该目录的规范路径，不含通配符、否定、绝对路径、反斜杠、空路径段、`.` 或 `..`。禁止把仓库根、源码根或通用测试/规格目录作为 managed ignore 项，至少包括 `tests/`、`src/test/`、`specs/`、`test/`、`src/`、`app/`、`lib/` 及其等价形式。已有目录、已有忽略规则或已有凭据均不改变这些限制。B 只校验产物路径已被忽略且未被跟踪；B 不修改 `.git/info/exclude` 或项目 `.gitignore`，失败时停止写入并回 A 修复。A 写入前、B 每次写报告或脚本前都用 `git check-ignore` 验证每个实际产物路径确实被忽略；未命中时不得写入。若任一实际目标已经被 Git 跟踪，只报告该事实并停止写入及任何自动索引操作，绝不执行 `git rm --cached`。非 Git 项目无需创建忽略文件，仍可写本地产物。

  ```gitignore
  # BEGIN business-self-test managed
  .self-test/
  # END business-self-test managed
  ```
- 范围记录需求/模块、纳入和排除项、项目类型。diff 使用用户指定基准；未指定时，有本地改动则比较 HEAD 与工作区（包括暂存内容、相关未跟踪代码），无本地改动则探测已有上游/默认分支的 merge-base。找不到或存在多个合理基准时询问一次，不猜分支。纯仓库输入没有 diff 时记“不适用”。
- A 必须先建立并验证插件维护的本地忽略元数据，再冻结快照扫描根。扫描根来自已记录的范围和影响地图，使用规范化仓库相对 POSIX 路径，逐项标明 `file` 或 `tree`；确认后 B 不得重新挑选、更换或缩小扫描根。Git 项目在每个根下用 Git 的 tracked 加 non-ignored untracked 视图枚举文件，保留缺失的 tracked 条目；非 Git 项目递归枚举相同扫描根。两者都按路径字节序排序，普通文件记录路径、类型和内容 SHA-256，符号链接记录链接目标字节的 SHA-256，缺失文件记录 `MISSING`，并记录算法版本、HEAD、基准 SHA 和 dirty 状态。快照 manifest 固定记录算法版本、扫描根、基准、规范化文件条目和逐文件 SHA-256；B 必须沿用相同扫描根和算法复算，并检测新增、删除、重命名和内容变化。
- manifest 使用 `snapshot-v1` 行协议：UTF-8 编码、仅 LF 换行并以一个 LF 结尾；固定顺序为 `version`、`head`、`base`、`dirty`，随后是按规范化路径 UTF-8 字节序排列的 `root` 行和 `entry` 行。每行字段以 TAB 分隔；路径先转为仓库相对 POSIX 路径，再按 UTF-8 字节做百分号编码，只保留 RFC 3986 unreserved 字符。`root` 行记录 `file|tree` 和路径；`entry` 行记录 `regular|symlink|missing`、路径及 SHA-256 或 `MISSING`。完整 snapshot manifest 必须位于 confirmation payload 内，以 `snapshot-v1`、UTF-8 和 LF 规范化序列化；`.gitignore` 摘要只删除唯一 managed block 的起止标记行及其中内容，保留 block 外字节。
- 对 `.gitignore` 的特殊摘要，先把 CRLF/CR 规范为 LF，要求恰好一对独占整行的 managed 起止标记，再删除从起始标记行到结束标记行及这些行各自的终止 LF；其余字符、空白和顺序保持不变，以 UTF-8 计算 SHA-256。该规范化结果只用于 `.gitignore` manifest entry，不改写用户 block 外内容。
- managed artifact 路径及其全部文件必须从扫描根、文件条目和 dirty 比较中显式排除，不依赖 `git check-ignore` 作为唯一依据。`.git/info/exclude` 位于 Git 元数据内，不进入源码 manifest；用户明确选择修改项目 `.gitignore` 时，插件维护的 managed block 不参与该文件的摘要，block 外的用户规则变化仍须记录。若 B 从调用链发现确认范围内存在 manifest 扫描根之外的相关源码，视为快照范围变化，回 A 扩充扫描根并重新确认。写入测试点、证据和报告不得使自身快照失效，也不得借此排除其他源码变化；执行范围内前后 manifest 不一致时不能混用证据。
- 业务版本如 v1、v2；纯措辞变更保持 TP-ID，业务语义新增/变更递增版本。稳定 TP-ID、历史测试点和历史结果可以作为草稿/证据基线，但历史确认没有任何自动效力，不能跨轮、跨快照或跨文件复用。
- 项目类型记录为 `GENERAL`、`BI` 或 `MIXED`。仓库同时包含交易/通用业务模块与报表、指标或数据 API 模块时使用 `MIXED`：按模块分别套用规则，同一轮可以同时覆盖两类模块，不因 BI 模块存在而把普通模块套入 BI 规则。
- BI 路由状态记录为 `BI_CONFIRMED`、`NON_BI_CONFIRMED` 或 `BI_UNCERTAIN`。只有命中报表/指标/数据查询业务信号或用户明确确认后，才读取 BI 参考规则；普通模块不加载该规则。
- 插件只维护包内两个技能和此契约；技能发布/验收材料不属于使用者每次自测的必需产物。

## 测试点 Markdown

`test-points.md` 文件头记录：范围、类型、来源、代码快照（可无代码）、业务版本、`confirmation-run-id`、确认载荷 SHA-256、状态 `待确认`、相对历史的变化摘要、待澄清项。其中确认载荷 SHA-256 是载荷外的完整性元数据，不属于被摘要内容；确认结果只记录在同目录 `confirmation.md`。

每个 `TP-###` 按以下业务字段组织，可共享流程前置而不重复抄写：

| 字段 | 内容 |
|---|---|
| 标题/目标 | 本场景要检验的业务结果 |
| 依据 | 需求章节、用户确认、实现观察或待确认假设；假设不是业务事实 |
| 优先级 | P0 核心/高影响，P1 直接异常/重要回归，P2 次要边界 |
| 角色与前置 | 身份、数据、业务状态 |
| 操作 | 业务入口、触发条件和步骤；不强制 API/SQL/选择器 |
| 预期 | 角色或下游可观察的业务终态、必要副作用及不变量；状态变化可写“保持不变” |
| 目标等级 | `L1` 或 `L2`；目标为 `L1` 时同时写明排除的下游边界 |
| 来源映射 | 原始用例 ID、代码/diff 位置、合并来源；没有就注明 |

同义场景合并并保留映射；不同角色、前置状态、边界或并发触发即使验证同一规则也可独立。正常与异常可分别判定时分别建点，共享执行流程不等于合并结果。已有脚本没有 TP-ID 时分配业务 ID 并记录脚本关联，不要求开发新增技术字段。

代码观察使用稳定 `OBS-###`：位置、触发路径、证据、影响严重度（高/中/低）、核实状态（待复核/已证实/已排除）、关联 TP 或未关联、下一步。严重度与证实程度分开；A 的观察必须被 B 继承。纯静态分析可以证实可推导的代码缺陷，但不是执行 PASS/FAIL。

## 本轮确认门禁

每次测试或回归都从 A 开始，先生成本轮唯一 `confirmation-run-id`；历史 `test-points.md` 只能作为草稿基线。A 必须在用户可见回复正文中展示本轮完整 TP 清单及每个 TP 的全部业务字段，同时展示相对历史的完整变化摘要，至少列出新增、删除、内容/预期变化、优先级变化、纳入/排除范围变化；无变化也要明确写“无变化”。少量 TP 一次展示；大量 TP 可按 TP 编号分页，每个分页页头必须包含 `第 n/N 页`、同一 `confirmation-run-id`、同一 payload SHA-256。确认请求只能出现在全部最终分页和完整变化摘要之后，消息开头或中间不得提前请求确认。文件链接、TP 数量、ID/标题目录或工具调用输出都不能代替完整展示。

只有用户在看到本轮全部最终页面和完整变化摘要后，明确确认该 `confirmation-run-id`、确认载荷 SHA-256、测试点和范围，才可执行。初始的“全面测试”“严格执行”“开始回归”等请求、原始需求、历史报告或旧确认都不是本轮确认。本轮性必须由当前用户发起的测试/回归请求中的连续交互证明：A 在该请求后新建 id、展示最终版，用户随后明确确认同一 id 和摘要，再由 A 直接交接 B。磁盘记录、相同代码快照、时间接近或字段完全匹配都不能单独证明本轮性；B 被直接调用而缺少这段当前交互证据时一律回 A。

`test-points.md` 用 `<!-- BEGIN CONFIRMATION PAYLOAD -->` 和 `<!-- END CONFIRMATION PAYLOAD -->` 包住唯一确认载荷。载荷必须包含 `confirmation-run-id`、范围及纳入/排除项、业务版本、完整 snapshot manifest、全部 TP 正文（含 ID 和八个标准字段）、假设/待澄清项及 OBS；所有可由用户修改并影响执行的语义都必须位于标记内。确认载荷 SHA-256 必须位于两行载荷标记之外，不参与自身摘要计算。状态、确认载荷 SHA-256 和变化摘要位于标记外；除此之外不得从载荷排除业务字段。摘要算法固定为：去掉两行标记，对其间内容仅把 CRLF/CR 换行为 LF，保持其余字节、空白、顺序和 Unicode 不变，以 UTF-8 编码后计算 SHA-256，将小写十六进制值记录在标记外。用户明确确认后，A 创建同目录 `confirmation.md`，逐项记录本轮 id、该 SHA-256、业务版本、TP-ID 范围、snapshot manifest、确认时间，以及用户明确确认的原意；该回执写入后不可修改。任意 TP 或其他确认载荷内容改变时，创建新的 `confirmation-run-id` 和不可变文件，重算 SHA-256，并重新展示全部最终分页和完整的最新变化摘要；全部展示完成后才能请求确认，不得沿用前一摘要下已展示的页面。确认载荷或代码快照变化后，原确认立即失效，回到 A 重新确认。

B 只接受上述字段完整、SHA-256 可按同一算法复算，且本轮 id、摘要和快照均匹配当前文件并具有当前交互证据的确认载荷。B 直接收到旧确认、旧报告、原始请求或仅有散乱/历史测试点时，必须回到 A，不得执行；不得以“同范围”“预期未变”或“已有有效确认”为由跳过本轮确认。

## 业务终态与证据边界

主流程先写明“谁在什么条件下最终看到什么”，再按已确认的业务边界识别必要副作用和结果；次数、时限、外部送达等只在需求有依据时作为断言，不从实现推定。队列入队、方法调用、HTTP 200、单测全绿或数据库中间状态仅证明相应环节，不能代替尚未观察的终态。同一 TP 可包含多环节证据，无需为每个技术环节单独建点。

有异步处理、外部依赖或运行时开关时，自动核对目标环境中与已确认范围相关的配置和实际激活路径：业务入口是否产生任务、范围内的消费者是否运行、依赖边界是否被调用，以及范围内的最终结果是否可观察。若确认范围仅到入队，下游消费不作为该 TP 的 PASS 门槛，须列为未验证/排除边界，不能宣称全链路通过。配置关闭可能是预期，不单凭关闭判产品缺陷；配置与预期冲突或链路未激活时，记录受影响的 TP/OBS。运行外部副作用前遵守权限和 mock 规则，不因要求完整链路擅自启用真实服务。

证据只能支持其真实到达的边界。例如发送适配器调用不证明收件箱收到邮件；支付回调成功不证明账户到账。获准的测试接收端/沙箱可验证至其实际接收或受理边界，不能宣称未经观察的真实提供商或用户侧结果。终态未验证且无反证时，按权限流程处理后记 NOT_RUN 或 BLOCKED，列明“已验证到哪一环、还差哪一环”；观察到必要断言违反预期则记 FAIL。不得靠缩小既有 TP 的语义取得 PASS。

### 终态门禁

每个 TP 的目标等级只能为 `L1` 或 `L2`：`L1` 为入口或中间状态，`L2` 为用户、下游系统或业务负责人可观察的最终结果。`L0` 只作为 `OBS-###` 的代码/配置观察等级。默认主流程目标为 `L2`；只有用户明确确认范围止于中间环节时才允许目标为 `L1`，并写明排除的下游边界。

B 必须在报告中记录目标等级与实际等级。实际等级低于目标时不得 PASS，按执行事实记为 `NOT_RUN` 或 `BLOCKED`；“自测未完成”只用于报告级结论。异步、通知、报表、导出、回调和外部服务以实际接收、展示或生效边界作为 L2；获准 mock 只能覆盖它实际替代的边界。

### 运行时激活门禁

执行前建立最小激活链：业务入口、生产者/写入方、消费者/worker 或查询服务、必要配置开关、依赖连通性、最终结果观察点。逐项记录 `ACTIVE`、`INACTIVE`、`UNKNOWN` 及证据。目标链中必需环节为 `INACTIVE` 或 `UNKNOWN` 时，相关 TP 不得 PASS；配置关闭与需求一致时可作为排除边界，但不得宣称全链路通过。优先使用项目真实 profile 和启动方式，不得只从配置文件静态推断“已启动”。

### 风险驱动覆盖门禁

从 diff、直接调用链、配置和业务影响建立影响地图，按模块而非文件数量选范围。命中支付/金额、权限/租户、状态转换、异步/定时、外部副作用、指标/聚合/导出、幂等/并发、删除或迁移任一风险时，至少覆盖主流程、一个直接异常、一个重复/重放或边界行为，以及一个受影响邻接流程；不适用项记录理由。已有测试只能做证据映射，不能替代缺失的风险类型。范围受限时优先 P0/P1，不能静默删除主流程。

## 时间与边界矩阵

当业务规则包含日期、时间、周期、到期、续费、定时任务或超时时，测试点的前置/操作/预期要保留业务时间语义，不要求用户填写技术字段。A 自动判断并记录适用维度：业务时区、普通时间、业务日内边界、UTC/本地换日、月末短月、闰年、夏令时（适用时）、连续周期及保存后的再计算。

最小矩阵是“普通点 + 业务日边界点 + 时区/换日点”；月/年规则再加月末短月和闰年，DST 仅在该地区适用时加入。不同点若触发路径或日期结果可能不同，不因同一自然日或同一不变量而合并。用户只给日期而未给时区/时刻时，A 先从明确业务约定或代码配置提取；仍不明确则标待澄清，不能擅自选一个时间代表全天。

B 必须尽可能验证完整链路：业务输入时间 → 应用计算 → 数据库/消息持久化 → 到期/下次执行或扣费 → 下一周期。只运行日期计算函数、只读代码、只看一个接口字段，不能证明数据库驱动的业务 TP PASS。缺少数据库或最终业务入口时，相关 TP 记 NOT_RUN/未验证并写明缺口；时间点未覆盖的场景不能被同一 TP 的其他时间点抵消。

## 环境、副作用与权限

执行任何可能写入的检查前，先将目标环境判定为 `NON_PROD`、`PROD` 或 `UNKNOWN`，并按下表执行；不得用用户确认绕过环境级禁令。

| 环境 | 只读检查 | 普通真实写入 | 支付、通知、删除、外部写入及其他不可逆或可能产生费用的操作 |
|---|---|---|---|
| `NON_PROD` | 在已有授权范围内允许 | 仅在已确认测试范围和已有授权内允许 | 仅在明确的测试账号、沙箱或隔离 mock 边界内，且用户单独确认目标、动作和执行上限后允许 |
| `PROD` | 在不扩大访问范围且不泄露秘密时允许 | 禁止 | 禁止 |
| `UNKNOWN` | 按 `PROD` 处理 | 禁止 | 禁止 |

`PROD` 和 `UNKNOWN` 仅允许只读检查，禁止任何真实写入；用户确认、已有凭据或时间压力都不能解除该禁令。无法明确证明 `NON_PROD` 时保持只读；需要写入才能验证的 TP 按权限流程记录为 `NOT_RUN` 或 `BLOCKED`，不得降级断言后判 PASS。

## 账号和 mock

1. 先检查已经授权的配置、测试账号与工具，合并同一缺失依赖及受影响 TP，一次说明用途和最小权限；已有授权不重复申请。使用平台权限申请机制或请用户配置本地环境变量/凭据文件，读取时不回显；不要求在聊天粘贴密码。
2. 优先请求测试账号/环境授权；用户可以直接选择“允许对指定边界 mock”。无法提供或拒绝真实依赖时，尚未决定 mock 的再询问一次，并说明未验证范围。mock 需用户明确同意；等待或沉默不是拒绝，也不算 mock 授权。
3. 等待期间内部 pending，在阶段报告中记 NOT_RUN/等待用户决定，继续不受影响项。用户部分提供时只处理剩余依赖。没有实质新信息不反复追问。
4. 用户已作出选择后，真实路径不可用且 mock 被拒绝、不适用或执行仍无法建立时，才记 BLOCKED，并附申请、决定、原因与下一步。权限仍在等待时不能用 BLOCKED 提前结束。用户要求先收口则交付“自测未完成”，保留待处理项。
5. mock 只替代获准外部边界，不替代被测业务逻辑，也不能预设库存/权限/幂等等被测断言为成功。测试原本要求真实提供商集成时，mock 内部结果只作补充，该真实断言仍未验证；要改变验收边界需明确记录用户确认。

## 结果与验证边界

分别记录执行结果、实际测试方式、依赖边界，禁止把 mock 当作与单元/API/E2E 互斥的层级。

| 结果 | 判定 |
|---|---|
| PASS | 该 TP 已确认业务边界内的所有必要断言真实执行并满足预期；可使用获准外部 mock，但必须注明 |
| FAIL | 执行证据证实必要业务断言违反预期；记录产品原因。脚本错误先分类，不直接当产品 FAIL |
| BLOCKED | 依赖/环境/工具问题已按申请流程处理仍无执行路径；也用于已确认无法消除的执行障碍，需原因 |
| NOT_RUN | 尚未执行、等待用户、预算不足或本轮未重跑；注明具体原因 |

实际方式可为单元/集成/API/浏览器/E2E；边界分别记录真实模块、测试库、提供商沙箱、获准 mock、未验证部分。没有执行只有代码阅读时，业务 TP 不得 PASS，静态发现单列。HTTP 200 只证明对应响应断言，不证明库存、权限等结果。

允许一个流程产生多个 TP 的证据；每条 PASS 都能定位必要断言。部分断言失败优先 FAIL，其他缺口同时记录；没有失败但必要断言受阻时 BLOCKED 或 NOT_RUN。未执行的真实集成 TP 不能被 mock 的内部 TP 通过所抵消。

例：用户已确认“在模拟支付事件输入下检验订单幂等”，实际订单服务与测试库重复处理后库存只减一次，可记 PASS/集成/支付事件 mock。支付平台签名、清算和真实回调送达未验证，不得称真实支付全链路通过。

## 报告与结论

报告依次包含：
1. 范围内结论（阶段性/最终）、execution run-id、confirmation-run-id、payload SHA-256、代码快照 manifest、业务版本、确认时间和耗时。
2. 产品缺陷及高风险待复核观察、未验证边界、清理残留及下一步。
3. TP 表：ID、结果、实际方式、依赖边界、必要断言摘要、证据/复现入口。一个表共享环境和命令时用链接避免重复。
4. OBS 复核表、权限/mock 决定摘要、数据清理与服务停止结果。

结论按以下顺序推导，不因其他 case 等待而隐藏已发现的问题：
- 任一已执行业务 FAIL，或存在已证实业务代码缺陷：**发现缺陷**，同时列出缺口。
- 无上述缺陷，但已确认范围内必要断言未验证、高风险观察待复核、代码快照过期或清理未完成：**自测未完成**。
- 其余：**本次范围自测通过**，紧邻结论写明 mock/沙箱边界和排除项，不代表正式 QA 验收或上线批准。

清理问题单列，不抹掉业务 PASS/FAIL，但会使原本可通过的总结变为未完成。报告保留脱敏复现脚本和日志；清除运行数据、测试进程、临时凭据。展示 PASS/FAIL/BLOCKED/NOT_RUN 数量与总数，不以局部通过率代表全范围通过。

## 回归与兼容

同一业务范围/预期不变时，可复用 TP-ID、历史测试点、脚本和历史结果作为本轮草稿/映射，但仍必须生成新的 `confirmation-run-id`、展示完整清单和变化摘要，并取得新的明确确认后才执行。改变业务预期时递增业务版本并更新受影响 TP。旧版 Markdown 缺少本轮确认门禁字段时一律回 A；可自动补技术映射，但不能从旧确认推导新确认，也不能因旧文件没新增字段要求全量重写。
