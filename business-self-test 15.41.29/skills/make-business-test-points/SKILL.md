# 生成业务测试点

开发提测前自测的统一入口。先明确业务预期，再让用户确认；确认后衔接执行技能。目标是发现本次改动的业务问题，并向测试人员交付可复现结果。

开始时读取 [共享契约](../business-test-contract.md)。它统一定义版本、确认、输出和结果，入口不另建一套状态。

## 快速参考

| 当前状态 | 动作 |
|---|---|
| 没有明确的提测前业务自测/回归意图 | 不触发本技能 |
| 输入尚未形成本轮确认载荷 | 建立范围、快照 manifest 和业务测试点 |
| 用户修改范围、TP 或其他载荷语义 | 重算摘要，完整重展示后再确认 |
| 本轮载荷已按契约确认且请求包含执行 | **REQUIRED SUB-SKILL:** 使用 `check-code-with-business-tests` |
| 确认载荷或快照 manifest 改变 | 原确认失效，创建新 confirmation-run-id |

## 输入与范围

- 接收需求、描述、截图说明、已有测试点、仓库、diff，支持组合或仅代码输入。先确认后端/前端/全栈；用户已明确说明时直接采用，未知类型时轻量探测后询问一次。历史测试点和 TP-ID 只作草稿基线，任何同范围历史确认均不得复用。
- 按契约记录仓库、变更基准和代码快照。先看变更，再追踪直接相关调用链、配置和现有测试；缺少仓库时只声明可读到的范围。代码片段或 diff 以外的行为不得当成已经检查。
- 默认快速自测：本次主流程、直接异常、受影响的高风险规则和必要邻接回归。列出纳入/排除项，不因出现“支付”就展开整个支付系统。用户要求扩大时再扩展。
- 只有仓库且没有明确模块/变更时，先发现候选范围，再询问范围；不得默认全仓验收。

### 影响地图与风险选择

先把 diff/需求映射为“业务入口 → 直接调用链 → 配置/依赖 → 用户或下游结果”，按模块记录影响，不按文件数量猜范围。命中支付/金额、权限/租户、状态转换、异步/定时、外部副作用、指标/聚合/导出、幂等/并发、删除或迁移时，生成覆盖矩阵：主流程 + 直接异常 + 重复/重放或边界 + 受影响邻接流程。每个不适用项写理由；范围受限时优先 P0/P1，不能静默删除主流程。

## 项目类型路由

先做轻量识别，不读取完整 BI 规则。按模块记录 `GENERAL`、`BI` 或 `MIXED`：同一仓库同时命中普通业务和报表/指标/数据 API 时使用 `MIXED`，本轮同时覆盖两类模块。

- BI 信号包括报表、看板、指标、统计分析、数据查询/导出 API，维度筛选、聚合/分组、趋势/排名/汇总，租户或行列数据权限，以及刷新/缓存/数据服务语义。
- 仅有 SQL、ORM、数据库表或普通详情查询，不足以判定 BI；订单、用户、支付、通知等交易模块继续走通用规则。
- 无法判断时记录 `BI_UNCERTAIN` 并询问一次“本次范围是否包含报表、指标或数据查询服务？”。用户确认后才读取 [BI 报表与数据 API 规则](../../references/bi-report-api-testing.md)。
- 识别结果写入 `test-points.md`，B 直接复用，不重复扫描。非 BI 模块不得加载该参考文件。

BI 模块的测试点必须保留业务最终结果：指标口径、维度/时间筛选、明细与汇总一致性、权限隔离、刷新/导出结果等。不能把“接口返回成功”或“查询有数据”当成业务预期。

## 第一性原理与去重

先根据需求与已确认规则明确“谁要得到什么结果”，再拆解相关的角色/权限、状态、资产或数据关系、失败边界及副作用。参考代码和测试定位实现与覆盖，不能用它们的现状证明业务正确。

每条主流程测试点把可观察的业务终态写入预期；涉及异步或外部副作用时，同时保留已确认的接收方、结果和必要失败行为。不要把“已入队/已调用/状态标记成功”改写为用户已经得到结果；技术环节由 B 映射，不为每层强制增加业务测试点。仅有代码时，将终态依据不明的部分标为待确认假设。

每条 TP 的目标等级只能为 `L1` 或 `L2`：默认目标为 `L2` 用户/下游可观察终态；只有用户明确确认范围止于入口或中间状态时才允许 `L1`，并写明排除的下游边界。`L0` 只用于 `OBS-###` 的代码/配置观察，不是可执行业务 TP 的目标等级。

每个预期注明依据：明确需求、用户确认，或待确认假设。只有代码时，先提取实现观察，再提出业务假设；第一性原理不能凭空证明“一笔流水”“支付后才扣库存”等领域规则。无依据的恢复时限、扣库存时机、分次支付策略集中列为待澄清。

按“业务规则 + 触发条件 + 角色/前置状态 + 关键预期”去重，合并同义点并保留来源映射。不同角色、边界、并发或重放可以验证同一不变量，仍是不同场景。已有脚本映射到 TP-ID，不用函数名替代稳定业务 ID；无状态变化的查询用例写“状态保持不变”，不用强造状态机。

对日期、时间、周期、到期、续费、定时任务或超时规则，额外拆出“时间轴维度”：业务时区、UTC/本地换日边界、当天早晚代表点、月末短月、闰年、夏令时（适用时）、周期连续计算和持久化字段。不能只用一个“1 月 31 日”的时间点代表整天；至少形成普通点 + 业务日边界点 + 跨时区/换日点，依据不明时把时区和边界列为待确认。相同日期的不同时间只有在代码和业务均证明等价时才能合并。

测试点由代理自动填写，用户只审业务。正常例：需求明确同一订单重复确认不能重复扣库存，则正常确认、顺序重放、并发确认可共享“只扣一次”的规则，各有独立触发和证据。SQL、浏览器选择器和测试命令留给 B。

## 代码观察

在相关调用链中发现异常时，按契约单列 OBS-ID、位置、触发路径、证据和影响。缺少局部检查不等于整个系统没有保护：先检查中间件、事务、唯一约束和上游校验。证据不足写“待复核”；不得当作已执行失败，也不能为了匹配代码修改预期。

涉及支付/退款/资金状态时，按需读取 [支付规则](../check-code-with-business-tests/references/payment.md)，只选与本次范围有关的风险。没有读到代码时明确“未做代码观察”。

## 确认与交接

每次测试或回归先创建唯一 `confirmation-run-id`。按契约由 A 先复用现有精确忽略规则，否则默认在 `.git/info/exclude` 修复并验证 managed block；只有用户明确选择团队共享时才修改项目 `.gitignore`。随后冻结扫描根和快照 manifest，再把本轮测试点写入不可变的 `runs/<confirmation-run-id>/test-points.md`。文件结构、摘要算法、完整展示、分页页头、变化摘要和确认顺序全部直接遵循共享契约，不在此另定义。

用户修改范围、TP 或其他载荷语义时，创建新的 `confirmation-run-id` 和候选文件并按契约重新展示；旧的未确认或已确认文件都保持不变。只有共享契约规定的当前交互证据完整时，才在同目录新建不可变 `confirmation.md`，不回写测试点文件。

请求包含自测/执行时，**REQUIRED SUB-SKILL:** 使用 `check-code-with-business-tests`；按名称定位并完整读取其 SKILL.md，由 A 在当前交互中直接交接。只要求生成测试点时在此结束；找不到 B 时保留待确认产物并说明缺失依赖。

同一业务范围回归可复用稳定 TP-ID、历史点和脚本，但每轮必须重新走本轮确认门禁；新增规则增补受影响点。A 不运行产品测试、不改产品代码。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 看到代码或 diff 就自动触发 | 只有明确请求提测前业务自测或回归时触发 |
| 用文件链接、标题目录代替完整审阅 | 按共享契约展示全部八字段 TP 和变化摘要 |
| 沿用旧确认或旧摘要 | 每轮创建新 id；任何已确认内容变化都重新生成和确认 |
| 默认修改项目 `.gitignore` | 先复用现有规则，否则写 `.git/info/exclude`；项目 `.gitignore` 只用于用户明确选择的团队共享规则 |
| 让 B 修改忽略配置 | B 不修改 `.git/info/exclude` 或项目 `.gitignore`；失败时回 A |
| 写回固定根级 `test-points.md` | 写入本轮不可变确认目录，旧文件只作草稿基线 |

## 完成检查

范围有界、预期有依据、同义点已合并且风险未误删、观察与事实分开、完整 TP 与变化摘要可审阅、确认记录与当前文件/快照匹配。尚未确认或确认失效时停在确认节点；只有本轮已确认的完整自测请求才交接 B，不把“生成完毕”当成自测完毕。
