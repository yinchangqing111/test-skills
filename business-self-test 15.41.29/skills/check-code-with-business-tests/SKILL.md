# 执行业务自测

读取已确认的业务测试点，自动选择可用且足以检验预期的方式，执行并交付可复现的 Markdown 报告。不是发布认证，也不自动修复产品代码。

开始时读取 [共享契约](../business-test-contract.md)；输入、状态、权限、mock 和结论以该文件为唯一规则来源。

## 快速参考

| 检查结果 | 动作 |
|---|---|
| 缺少当前交互确认或绑定字段不匹配 | 回 A，不执行 |
| payload 摘要或快照 manifest 不匹配 | 确认失效，回 A |
| 产物路径未被忽略或已经被跟踪 | 停止写入，回 A；B 不修改 `.git/info/exclude` 或项目 `.gitignore` |
| 环境是 `PROD` 或 `UNKNOWN` | 只读；任何真实写入禁止 |
| 确认、快照、环境和权限门禁全部通过 | 创建 execution run-id 并执行 |

## 入口与自动规划

输入必须是 A 在当前测试/回归请求中按共享契约生成、完整展示、明确确认后直接交接的不可变测试点文件及同目录 `confirmation.md`。B 只接受契约规定的完整绑定和当前交互证据。任一入口条件缺失、过期或不匹配时，**REQUIRED SUB-SKILL:** 使用 `make-business-test-points`；按名称定位并完整读取其 SKILL.md，重新生成、展示并确认，B 不得执行。

根据 A 记录的项目类型路由执行：`GENERAL` 只用通用规则，`BI` 才读取 [BI 报表与数据 API 规则](../../references/bi-report-api-testing.md)，`MIXED` 按模块同时执行两套规则。不得因为同一仓库存在 BI 代码就把普通交易模块改按 BI 规则执行。

1. 执行前对不可变测试点文件复算 payload SHA-256，沿用其中冻结的扫描根和算法复算快照 manifest，并校验全部确认绑定；同时继承观察项。任一差异都按契约使确认失效并回 A。通过后才发现项目命令、服务和测试，不要求用户填写技术配置。
2. 按共享契约判定 `NON_PROD`、`PROD` 或 `UNKNOWN` 并应用环境权限矩阵；不得另建生产例外。
3. 先做运行时激活预检：确认真实 profile/启动方式、业务入口、生产者、消费者/worker 或查询服务、配置开关、依赖连通性和最终观察点。每项记录 `ACTIVE`/`INACTIVE`/`UNKNOWN` 与证据；必需项未激活或未知时，相关 TP 不得 PASS。
4. 以业务流程分组，内部映射 TP-ID 到必要断言、可执行入口、所需依赖和清理方式。不新建强制 JSON 工件，不按测试层数堆脚本。共用登录/数据时区分用例隔离和顺序依赖，每个 TP 仍有自己的断言证据。
5. 优先复用能覆盖关键断言的现有测试；HTTP 200、测试套件全绿或仅有同名测试不能证明业务覆盖。不足时在本轮执行目录生成最小复现脚本，不修改业务代码、正式测试或项目依赖配置。写入任何报告、证据或脚本前，按契约复查实际路径已被 `git check-ignore` 命中且未被跟踪；否则停止写入并回 A，B 不修改 `.git/info/exclude`、项目 `.gitignore` 或其他忽略配置。
6. 选择最小充分验证：后端通过真实 API/消息/任务及最终状态；前端涉及交互必须使用真实浏览器点击、输入、导航；全栈核验跨层结果。只覆盖部分流程叫 API/集成测试；覆盖约定完整业务边界才叫 E2E。接口数量和有无浏览器不决定后端 E2E，浏览器加 mock 也不代表真实全栈 E2E。
7. 为每个主流程记录“目标等级/实际等级”：TP 目标只能为 `L1` 或 `L2`，`L0` 只用于静态观察。列出“入口 → 中间状态 → 消费/执行 → 已确认业务终态”的证据链；实际等级低于目标时不得 PASS。若旧 TP 只写了中间状态，按原业务依据补充可观察预期；涉及新业务语义时交 A 确认，不擅自扩张验收范围。

8. 对 `BI`/`MIXED` 中的 BI 模块，沿“数据入口 → 查询/加工 → 指标或数据 API → 报表/导出可见结果”执行。除通用链路外，必须验证已确认的指标口径、维度和时间筛选、明细/汇总关系、数据权限及刷新/导出一致性；HTTP 200、SQL 成功或字段存在只能作为局部证据。

9. 遇到日期、时间、周期、到期、续费、定时或超时规则，不得只验证一个时间点或只调用底层计算函数。按 A/契约的时间轴矩阵至少执行普通时间、业务日内边界、业务时区与 UTC 换日边界；涉及月/年再覆盖月末短月和闰年，涉及夏令时才加入 DST。沿真实链路核对输入时间、应用/数据库保存值、到期值、下次执行/扣费值及连续周期结果；数据库或最终业务入口不可用时，相关 TP 记 NOT_RUN/未验证，不得用静态推导或孤立函数 PASS。

## 执行与异常

- 先执行已确认的主流程和高风险点，再跑必要回归。遵守用户时间预算；未指定时以约 15 分钟有效执行时间为首轮目标（不含用户等待），不是完成承诺。预算到达保留已发现问题，剩余点记 NOT_RUN/预算不足，不缩水预期或伪报通过。
- 缺账号、权限或依赖，按契约申请和等待；相同依赖合并处理，其他可执行点继续。涉及支付时读取 [支付规则](references/payment.md)。用户批准 mock 后只替代指定边界，记录哪些内部断言真实运行、哪些外部边界未验证。
- 对每条必要断言记录预期、实际、时间、命令/操作及脱敏证据，并在报告中记录 `confirmation-run-id` 和确认绑定信息。使用本轮输出；若测试期间测试点文件或代码快照改变，确认与受影响证据立即失效，停止执行并回 A 重新确认，不得仅重跑或列为未验证后继续沿用确认。
- 失败先分类：产品缺陷、测试脚本问题、环境/权限问题、需求歧义。产品缺陷记录位置、复现与影响，不自动修代码；本轮生成脚本的问题可最小修正并重跑，保持业务断言，最多两次不同根因尝试；正式脚本或配置需要修改时先征求授权。环境只在已有授权范围修复。预期歧义交回 A，仅暂停受影响点。
- 新增业务场景交 A 增补确认；对原场景补充技术断言不改变业务预期，无需再次确认。执行中异常及 A 的观察项逐项复核，保留已证实/待复核/已排除及证据，不把静态怀疑伪装成执行 FAIL。
- 为测试数据分配本轮标识；完成、失败或中断都用 finally/teardown 清理并核实，只清理本轮创建的资源和自己启动的服务。无法清理时记录残留标识、影响和恢复步骤，保留业务结果并按契约影响结论。日志和复现脚本保留，账号/token 不进入文件或聊天。

## 报告与回归

创建唯一 execution run-id。等待用户时可按契约写入递增序号的不可变阶段报告；阶段报告不占用最终 `test-report.md`。收口时在 `runs/<confirmation-run-id>/executions/<run-id>/test-report.md` 一次写入最终报告，先给本轮结论、确认绑定、产品缺陷、未验证边界及复现入口，再列每个 TP 的结果与证据；不回写测试点业务内容。NOT_RUN/等待用户决定不等于最终 BLOCKED。

修复后的回归可沿用未变的 TP-ID、业务点和脚本，但必须回 A 先冻结新的扫描根和 snapshot manifest，把它们写入新 `confirmation-run-id` 的载荷，再完整展示 TP 与变化摘要并取得明确确认；B 随后复算同一 manifest 后执行。不得沿用业务确认或旧 PASS。重跑失败点及受影响邻接流程，用户要求全量则全量；未重跑点引用旧记录并标“本轮未执行”。保存新报告，不覆盖既有证据。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 只看磁盘确认或旧报告就执行 | 必须存在共享契约规定的当前交互证据 |
| B 重新选择较窄的快照文件 | 沿用 A 冻结的扫描根和 manifest 算法 |
| 路径未忽略时由 B 修忽略配置 | 停止写入并回 A；B 不修改 `.git/info/exclude` 或项目 `.gitignore` |
| HTTP 200、入队或单测通过就判业务 PASS | 证据只支持实际到达的业务边界 |
| 生产凭据或用户确认被当成写入授权 | `PROD`、`UNKNOWN` 永远只读 |
| 覆盖旧报告或测试点 | 每次确认和执行都写入新的不可变目录 |

完成前核对：`confirmation-run-id` 与绑定字段仍匹配、每个确认点有状态/原因，PASS 的必要断言有本轮证据，mock 授权范围可追溯，观察项未丢失，清理有结果，结论满足契约的优先级。生成报告不等于所有测试通过。
